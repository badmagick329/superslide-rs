# Rendering and platform stack

Status: Accepted (2026-10-10), once SSR-14 verified phase 1 of the [v1 build plan](../plans/active/2026-10-10-v1-build.md) on it: 50 MP JPEGs page with no visible wait, and a quarter-size image of 1 px stripes shows no moiré while panning.

## Context

The [v1 scope](2026-10-10-v1-scope.md) drops transitions, which were the original's main GPU use. Zoom and pan of 24–50 MP images must stay smooth, and shrinking a large image to window size must not alias.

## Decision

| Concern | Crate |
| --- | --- |
| Window, fullscreen, monitors, input | `winit` |
| Drawing | `wgpu`: one textured quad with mipmaps, generated by a GPU pass after upload |
| Decoding | `image`; `zune-jpeg` for JPEG speed |
| Downscaling images over the texture limit | `fast_image_resize` |
| EXIF orientation (read only) | `kamadak-exif` |
| Info overlay, preferences screen, notices | `egui` on the same `wgpu` device, through `egui-wgpu` and `egui-winit` |
| Recycle Bin, clipboard, file dialogs | `trash`, `arboard`, `rfd` |
| Folder scanning | `walkdir` |
| Preferences and session file | `serde` + `toml` |

The GPU stays without transitions: with a sampled, mipmapped texture, zoom and pan cost one draw call. CPU drawing would rescale the image on every frame.

## Consequences

- Images larger than the device's maximum texture size are downscaled at load rather than tiled.
- wgpu does not generate mipmaps, so the project owns a mip-generation pass.
- No software render path is written: WARP covers machines without a suitable GPU.
